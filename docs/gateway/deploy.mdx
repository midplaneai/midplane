title: "Deploy the gateway"
description: "What the gateway is, where to run it, and the steps to get it running on your machine, on a server with Docker, or on a platform."
---

The gateway is the part of Midplane that runs in your network. It's a small
program next to your databases: agents connect to it, it checks each statement
against your policy and records it, and only then runs it. It holds your
connection strings, and it connects out to Midplane Cloud to get your policy.
Nothing connects in to it but agents.

## Where to run it

<Columns cols={2}>
  <Card title="This machine" icon="laptop" href="#this-machine">
    To try Midplane. Only agents on this machine can use it.
  </Card>
  <Card title="A server, with Docker" icon="server" href="#docker">
    For a team or production: agents anywhere reach it at an HTTPS URL.
  </Card>
</Columns>

Run it where it can reach your databases: on your laptop for a local or cloud
database, inside the VPC for a private one.

## This machine

You need Node 24.16 or newer, and macOS, Linux or WSL on Windows.

<Warning>
  The gateway runs as you, so an agent that runs commands as you, such as
  Claude Code with its shell, can read `secrets/*.dsn` and connect to the
  database without Midplane. Use this machine to try Midplane; to hold such an
  agent to your policy, run the gateway as another user or on another host.
</Warning>

<Steps>
  <Step title="Create an enrollment token">
    In your project, open step 1 of the setup (or **Gateways**, then **Set up
    a gateway**), and click **Create enrollment token**. The gateway uses it
    once, to join your project. Keep the page open: the command below it now
    holds the token.
  </Step>
  <Step title="Run setup">
    Choose **This machine** and run the command in a terminal. It runs
    `midplane setup`, which asks for each database's connection string
    ([prepare your database](/prepare-database)). What you paste isn't shown,
    and stays in the gateway's folder: it never reaches Midplane Cloud.
  </Step>
  <Step title="Check each database">
    Setup connects as the gateway will and says what it found, such as `ok:
    database app on db.internal, 12 tables`. If it fails, it says why: paste
    a corrected string, or type `keep` to save it anyway. It suggests a name
    for each database new to the project, such as `shop`, which you can
    change.
  </Step>
  <Step title="Start it">
    Setup joins your project, writes the gateway's folder where you ran it,
    such as `gw-k3m9x2qa`, and starts the gateway. The page shows it
    connected. It keeps running in that terminal; `Ctrl-C` stops it, and
    `npx -y midplane@latest gateway --config gw-k3m9x2qa/midplane.yaml` starts
    it again.
  </Step>
</Steps>

Agents on this machine reach it at the `http://gw-….localhost` URL setup
prints. Setup takes the first port from 7433 to 7442 that is free when it
runs, so a gateway that was stopped then may have its port taken: give the
new one another with `--port`.

## Docker

You need a server with Docker and a URL for the gateway, such as
`https://midplane.example.com`. The gateway serves HTTPS itself whenever it's
reachable from other machines, with a certificate it gets from Let's Encrypt
and renews, or with your own.

<Steps>
  <Step title="Point the URL at the server">
    Point the URL's DNS at the server: an `A` record, and `AAAA` if it has
    IPv6. Then, for the certificate:

    <Tabs>
      <Tab title="Automatic certificate">
        Open ports 80 and 443 to the internet, or the port agents will use
        instead of 443. Let's Encrypt checks port 80 before it issues the
        certificate, and again each time the gateway renews it: there it
        reaches a listener that answers its challenge and nothing else.
        Getting the certificate agrees to Let's Encrypt's [subscriber
        agreement](https://letsencrypt.org/repository/).
      </Tab>
      <Tab title="My own certificate">
        Open port 443 to the agents that will use the gateway, or the port
        they use instead. On the server, save the certificate and its key as
        `/etc/midplane/tls/tls.crt` and `/etc/midplane/tls/tls.key`. The image
        runs as uid 1000, which must be able to read both, such as after `sudo
        chown 1000 /etc/midplane/tls/tls.key`. Setup checks that the
        certificate is for the URL, current, and matches its key. The gateway
        reads them again every 10 minutes, so a renewed certificate is served
        without a restart. Use your own for an IP address, which Let's Encrypt
        doesn't certify, or a server port 80 can't reach.
      </Tab>
    </Tabs>
  </Step>
  <Step title="Create an enrollment token">
    In your project, open step 1 of the setup (or **Gateways**, then **Set up
    a gateway**), and click **Create enrollment token**.
  </Step>
  <Step title="Enter the gateway's URL">
    Choose **A server (Docker)** and enter the gateway's URL: `https://` and
    the name you pointed at the server, such as
    `https://midplane.example.com`. Agents reach the gateway at it. Under
    **Certificate**, keep **Automatic (Let's Encrypt)** or choose **My own**.
    With an automatic certificate, the page lists what must be true before
    you run the commands, and looks up where the name points now, such as
    `midplane.example.com points at 203.0.113.7`. If it says the name
    doesn't resolve yet, wait a few minutes for the record and press **Check
    again**. The page then shows two commands, with the token in them.
  </Step>
  <Step title="Run setup in the image">
    Run the first command on the server. Setup asks for each connection
    string and tests it from inside the container, where `localhost` is the
    container: use the database's host as the server's network knows it.
    With an automatic certificate it then gets one for the URL, saying `ok:
    valid until` and its date; if Let's Encrypt can't reach the server, it
    says why ([troubleshooting](/troubleshooting#the-gateway-does-not-connect)),
    removes what it wrote and leaves the token unused. It writes the config,
    the connection strings, the certificate and the gateway's identity to a
    Docker volume named after the gateway, such as `midplane-gw-k3m9x2qa`,
    and joins your project.
  </Step>
  <Step title="Start it">
    Run the second command. It starts the gateway from that volume, and again
    whenever the server restarts. The page shows it connected; `docker logs
    -f midplane-gw-…` shows what it says. An automatic certificate is renewed
    in its last 30 days, without a restart.
  </Step>
</Steps>

For production, replace `:latest` in both commands with a version you
[verified](/releases).

## Other setups

<AccordionGroup>
  <Accordion title="Behind your TLS proxy">
    If a proxy or load balancer on the same host already serves TLS for the
    URL, keep the gateway on loopback and have the proxy forward the URL to
    it, keeping the `Host` header.

    - **With `npx`:** follow [this machine](#this-machine). Then add the URL
      to `public_urls` in the gateway's `midplane.yaml`, such as
      `public_urls: [http://gw-k3m9x2qa.localhost:7433,
      https://midplane.example.com]`, and restart it. A URL added after the
      gateway joined waits on the project's **Gateways** page until an owner
      or admin presses **Register**. Point the proxy at
      `http://127.0.0.1:7433`, or the port setup chose.
    - **With Docker:** [write the config yourself](#write-the-config-yourself),
      with `listen: { host: 127.0.0.1, port: 7433 }`, your URL in
      `public_urls` and no `tls`, and run the container with `--network host`
      (Linux only). The gateway registers the URLs in its config when it
      first starts.
  </Accordion>
  <Accordion title="A platform without a disk">
    Some platforms keep no files across restarts, so the gateway can't keep the
    identity it gets when it joins. Enroll it once and store the identity as a
    secret instead:

    1. [Write the config yourself](#write-the-config-yourself), with
       `link.identity: { env: MIDPLANE_IDENTITY }`.
    2. Run `npx -y midplane@latest enroll --config midplane.yaml` with the
       token in place. It prints the identity as one line of JSON. It reads the
       whole config, so every file and variable it names must exist there.
    3. Store that line in the platform's secrets as `MIDPLANE_IDENTITY`, and
       delete any copy: it holds the gateway's private key.

    Most platforms end TLS at their edge and forward plain HTTP, which the
    gateway refuses: run a TLS proxy beside it, as in
    [hosted agents](/gateway/hosted-agents). Mount a volume for the audit log
    if you want to keep it.
  </Accordion>
  <Accordion title="Write the config yourself">
    For what setup doesn't cover, such as a proxy in front, a secret manager
    or Kubernetes, write the config by hand. The gateway joins the project
    the first time it starts, with the token from the file the config names.

    1. Make the gateway's folder, with a `secrets/` folder closed to other
       users: `mkdir -p gw/secrets && cd gw && chmod 700 secrets`.
    2. Make the mask salt: `openssl rand -hex 32 > secrets/mask-salt`.
    3. With an editor, write each connection string to
       `secrets/<database id>.dsn`, and the token to
       `secrets/enrollment-token`. The token is the `--token` value in the
       command the page shows after **Create enrollment token**.
    4. Save the config as `midplane.yaml`, with a line per database:

       ```yaml
       listen: { port: 7433 }
       public_urls: [http://gw-k3m9x2qa.localhost:7433]
       audit: { file: audit.db }
       mask_salt: { file: secrets/mask-salt }
       link:
         cloud_url: https://eu.app.midplane.ai
         identity: { file: identity.json }
         enrollment_token: { file: secrets/enrollment-token }
       databases:
         shop: { dsn: { file: secrets/shop.dsn } }
       ```

    5. Start it: `npx -y midplane@latest gateway --config midplane.yaml`.

    A database the config names that the project lacks shows on **Gateways**
    as `in its config, not in this project`, with **Add** beside it. In
    Docker, mount the folder read-only at `/etc/midplane`, where the image
    reads `midplane.yaml`, and let uid 1000 read the secrets (`sudo chown -R
    1000:1000 secrets`). Put what the gateway writes (`audit.file`,
    `link.identity` and `link.bundle_cache`) under `/var/lib/midplane/`, on a
    volume. Every key is in [configuration](/gateway/configuration).
  </Accordion>
  <Accordion title="What the gateway's folder holds">
    ```text
    gw-k3m9x2qa/
      midplane.yaml          the config, with no secrets in it
      secrets/               closed to other users
        shop.dsn             a connection string per database
        mask-salt            the key for hashing masked values
      identity.json          the gateway's key, written when it joins
      audit.db               the audit log
      bundle.jws             the newest policy, for a restart with the cloud down
      acme/                  with an automatic certificate, closed to other users
        cert.pem             the certificate, renewed in its last 30 days
        key.pem              its key
        account.key          the Let's Encrypt account's key
    ```

    In Docker, the same files are in the gateway's volume, such as
    `midplane-gw-k3m9x2qa`. Keep the folder or the volume: a new one is a new
    gateway, with a new mask salt.
  </Accordion>
</AccordionGroup>

Every setting is in [configuration](/gateway/configuration). If the gateway
doesn't connect, see [troubleshooting](/troubleshooting).

*Tested by* `apps/gateway/scripts/package-smoke.ts` (setup with the packed
npm package; setup then the gateway in the image on one volume, with your own
certificate and with an automatic one from Pebble, Let's Encrypt's test CA,
in CI's `package` job).
